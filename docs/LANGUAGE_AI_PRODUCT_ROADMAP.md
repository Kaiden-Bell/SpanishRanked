# Language AI — Product Vision, Learning Design & Roadmap

> **Status:** Living design guideline  
> **Last updated:** November 10, 2026  
> **Scope:** Level 2 onward. Decisions from the post-MVP product review, the 30-question feature-planning discussion, and the compatibility audit of November 10, 2026.  
> **Authority:** `MVP_DESIGN.md` governs Level 1. This document governs what comes after it and owns the order of post-MVP work. Build details for the first Level 2 milestones are in `LEVEL2_RECAP_REVIEW_PLAN.md`.

## 1. Product vision

Language AI is a self-hosted, offline-first language-learning application that helps people **retain, understand, and use a language**, not simply collect XP. It combines manual study logging, a personal learning history, short reviews, evidence-based skill profiles, practical language activities, and game-style progression.

The initial focus is Spanish, but avoid hard-coding Spanish-only assumptions into core learning records where practical.

### Guiding principles

1. **Learning evidence is not XP.** XP rewards engagement; demonstrated performance informs skill estimates.
2. **Recognition is not mastery.** Seeing a word, saying you know it, answering correctly once, and using it consistently are different stages.
3. **Practice should transfer.** Revisit a concept in new sentences and real conversations rather than repeatedly asking an identical question.
4. **Keep the learner in control.** Suggest extracted learning concepts for confirmation; don't silently assume a study note proves mastery.
5. **Review without overwhelming.** Prefer short, useful exercises and few unfamiliar words at a time.
6. **Use deterministic logic first.** Verified content and question templates should work without an LLM; use AI where it genuinely adds value.
7. **Support recovery.** Missed days, broken streaks, wrong answers, and failed boss battles should lead to constructive practice, not dead ends.
8. **Keep features modular.** Recaps, reviews, challenges, listening, speaking, and boss battles should share learning evidence but remain independently maintainable.

## 2. What exists today

Checked against the repository on November 10, 2026. Level 1 is in release check (Milestone E in `MVP_DESIGN.md` §11).

**Built:**

- One compose project: the app, LanguageTool, and optionally Ollama.
- Study-session logging. Each session saves 3 to 5 terms and 2 to 3 learner-written sentences.
- An append-only XP ledger with ranks, streaks, and a daily cap per source.
- Quick Assessment: three written-answer questions generated by the local model from the learner's own recent terms.
- Model grading with a HIT, PARTIAL, or MISS outcome per target concept, saved as concept evidence.
- An API that lists past assessments.

**Not built:**

- Any recap or review screen, and any return-visit feature.
- Multiple-choice or fill-in-the-blank questions. Every question is a written answer.
- Questions that work without the local model.
- A personal dictionary, self-reported familiarity, or a review queue.
- Skill estimates. The dashboard says "Not yet assessed".
- A page for quiz history.
- Listening, speaking, challenges, and boss battles.

The owner used the Level 1 app for several days, progressed toward **Pre-Learner III**, and found that it gives no reason to return between study sessions. That gap drives the first Level 2 milestones.

## 3. Confirmed feature decisions

| Area | Decision |
| --- | --- |
| Return visit | Quickly recall prior study and understand a useful concept or word in context. |
| Listening goal | Hear natural Spanish and identify important words, especially verbs/nouns, while progressively understanding connecting words too. |
| Listening errors | Show missed words, replay more slowly, then test the concept in a new sentence. |
| Listening difficulty | Everyday realistic conversations, with few unfamiliar words at a time. |
| Word familiarity | Combine self-reported familiarity with observed quiz performance. |
| Daily Recap | Short summary of recent learning; not limited to yesterday if several days were missed. |
| Daily Review | Optional activity separate from reading the recap; aim for ~5 minutes. |
| Review content | Mix multiple choice, fill-in-the-blank, and short written answers. |
| Review length | Target up to five mixed items. Use fewer if there is insufficient good material; never pad a quiz. |
| Question generation | Heavily favor verified templates; AI only when needed, not as the default. |
| Review mistakes | Finish the first round, then run a second round on missed concepts with different questions. |
| Review results | Explain mistakes and show improvements and remaining weaknesses. |
| Review XP | Small completion reward plus correct-answer bonuses; lower XP for correct retries; daily cap. |
| Review XP ledger | One XP event per review session, counted against its own daily cap, separate from quizzes. |
| Skill impact | Record every attempt; update skill estimates gradually using repeated evidence. |
| Weak concepts | Offer immediate targeted practice and schedule future review. |
| Vocabulary extraction | Suggest words/concepts from session notes; learner confirms before saving. |

| Daily/weekly challenges | Shared rotating challenge bank, not personalized challenge selection for the initial version. |
| Challenge completion | Require demonstrated learning when applicable; completion never removes words from future practice. |

| First Level 2 milestone | **Daily Recap, then Daily Review**, started after Level 1 is released. |

### Where the first Review release falls short of these decisions

The first release of Daily Review reuses the Level 1 quiz generator and grader. It is deliberately smaller than the table above:

- **It needs the local model.** If the model is down, the Recap still shows and Review says it is unavailable.
- **It is written-answer only, with three questions per round.** Multiple choice, fill-in-the-blank, and the five-item target arrive with the template engine (§7).
- **It uses the terms the learner already enters in the study form.** Suggesting concepts from free-text notes comes later.

These are accepted gaps with a milestone attached (§13), not changes to the decisions.

### Important distinction: completion versus mastery

- **Encountered:** A word or concept was studied or confirmed from notes.
- **Self-reported familiar:** The learner says they recognize it.
- **Demonstrated:** The learner answered or used it correctly in an assessment.
- **Consistently demonstrated:** Multiple independent successes across time and contexts support higher confidence.
- **Challenge completed:** A specific challenge's requirements were met; this does not retire the underlying words.
- **Mastered:** A conservative, evidence-backed estimate; never assume permanent knowledge.

These are conceptual states, **not finalized database enum values**.

## 4. Daily Recap & Review — first Level 2 priority

This section describes the intended experience. What the first release builds, and how, is in `LEVEL2_RECAP_REVIEW_PLAN.md`.

### 4.1 Learner experience

**A. Study session**

1. Learner logs a session and writes a short note about what they studied.
2. The app suggests vocabulary and grammar concepts found in the note. *(Later. Today the learner types the terms directly.)*
3. Learner confirms, edits, or rejects suggestions.
4. Confirmed concepts enter learning history as *encountered*, not mastered.

Example note: `Studied present-tense verbs: tener, querer, poder.`  
Possible suggestions: three verbs, present-tense conjugation.

**B. Daily Recap (read-only)**

- Display a **short, readable summary** of recent learning.
- Highlight recently encountered concepts, demonstrated improvements, and concepts needing practice.
- Draw from older sessions if the learner has been absent for several days.
- Allow the learner to leave after reading; a quiz is not mandatory.
- Avoid pretending to know what improved when evidence is insufficient.

**C. Daily Review (optional)**

- Target about **five minutes**, typically around five questions.
- Mix multiple choice, fill-in-the-blank, and short written answers.
- Choose from verified templates and known concepts.
- Balance weaknesses with newer learning.
- Include occasional checks of words marked familiar by the learner.
- If only two meaningful questions are available, present two—not five filler questions.
- Do not require an LLM to create the normal question set. *(Not met by the first release; see §3.)*

**D. Round 2: missed concepts**

- After the first round, identify concepts missed.
- Present different questions or sentences on those concepts.
- Preserve original incorrect answers as evidence.
- A successful retry is useful evidence, but does not rewrite the first attempt as correct.
- The concept can reappear in future reviews, even after a successful retry.

**E. Results**

Show:

- First-attempt accuracy and retry results **separately**.
- Explanation for mistakes and relevant correct forms.
- XP earned, with completion and accuracy rewards distinguished.
- Evidence-backed improvements and remaining weak areas.
- Concepts queued for future practice.

### 4.2 XP policy (values TBD)

The **rules** are decided; numeric constants are **not**.

```text
daily_review_xp =
    completion_xp
  + first_try_correct_count * first_try_xp
  + retry_correct_count * reduced_retry_xp

daily_review_xp = min(daily_review_xp, remaining_daily_review_xp_cap)
```

Requirements:

- `reduced_retry_xp < first_try_xp`.
- The whole review is **one ledger event**, awarded when the review session closes. The per-question detail stays with the questions and the evidence, so the award can be audited.
- Reviews have **their own daily cap**. A review never uses up quiz XP, and a quiz never uses up review XP.
- Define whether completing multiple reviews in a day can earn completion XP again; recommendation: prevent repeated farming.
- XP must never be used as a direct substitute for skill mastery.

### 4.3 Gradual skill updates

Every response should be recorded, but skill ratings should not swing sharply after a single quiz.

Suggested rules to explore:

- Track the tested **concept** and **modality** (e.g., vocabulary recognition, writing a verb form).
- Track first attempt versus retry, correctness, and whether help was used.
- Prefer performance across **different contexts** and **different days**.
- Use a minimum evidence threshold before displaying a confident improvement claim.
- Keep raw evidence so the scoring algorithm can be improved later.

**Open design decision:** exact weighting, evidence thresholds, and decay/review scheduling formula. Start simple and make it testable.

## 5. Personal dictionary and learning history

The personal dictionary is a persistent record of vocabulary and concepts, not a list of permanently completed words.

It should support:

- Word/lemma, language, meaning/sense, part of speech, and example context.
- Confirmed source (study session, quiz, listening, conversation, etc.).
- Learner-reported familiarity, separately from measured performance.
- Evidence of success/failure by activity and context.
- Last encountered, last tested, and future review eligibility.
- Reappearance of familiar or previously successful words in new contexts.

**Important:** A word marked familiar may still be tested occasionally. Passing a daily challenge does not delete it from the review pool.

### Data model: what exists and what each milestone adds

Extend the existing tables. Do not create parallel ones. Milestone names are defined in §13.

| Need | Today | Added in |
| --- | --- | --- |
| Study sessions with notes | `study_sessions`, `study_terms`, `study_sentences` | Nothing needed. |
| Canonical concepts | `concepts` holds only language, token, and category | L2-M3: meaning, part of speech, example context. |
| Learner-to-concept link and familiarity | Not present | L2-M3: a new learner-concept table. |
| Evidence per response | `concept_evidence` with modality, evidence type, outcome, assistance level | Nothing in L2-M1 or L2-M2. See §6 for the one known gap. |
| Review sessions | Not present | L2-M2: a new `review_sessions` table. |
| Review questions | `assessments` and `assessment_items` | L2-M2: a review-session link and a round number on `assessments`. |
| Review XP | `xp_events` accepts only study sessions and assessments | L2-M2: allow a `REVIEW` source. |
| Future-review queue | Not present | L2-M3. |
| Challenges | Not present | With the challenges milestone. |
| Boss attempts | Not present | With the speaking and bosses milestone. |

## 6. What future features need from evidence today

Listening, speaking, and boss battles are years of work away, but they decide how evidence should be stored now. The audit checked the current evidence table against them.

**Already covered:**

- **Modality.** Evidence already accepts `LISTENING` and `SPEAKING` alongside reading and writing, so new activities need no change to record their own skill.
- **Assistance.** Evidence already records assisted versus unassisted. A simplified or rephrased speaking prompt, or a slowed listening replay, can be stored as assisted.
- **First attempt versus retry.** Once an assessment carries a round number (L2-M2), every evidence row can be traced to its round through the question it came from. Evidence rows need no new column.
- **Raw history.** Evidence is append-only and never rewritten, so scoring formulas can change later.

**Gaps to keep in mind:**

- **Context.** Evidence links to a question, and the question holds its prompt. Nothing identifies the sentence or scenario in a way that can be compared, so "succeeded in three different contexts" cannot be counted yet. Design this with the template engine, which is the first feature to reuse sentences.
- **Evidence without a question.** An evidence row must point at a study session or an assessment question. Conversation turns and listening clips are neither. They will need their own source link when those features are built.
- **Exposure.** Study sessions do not write evidence today. Only grading does. "Encountered" is read from the saved terms instead, which is enough for the Recap.

**Rule for new work:** a feature may add a new source of evidence, but it records into the same evidence table with an honest modality and assistance level.

## 7. Question-template engine

### 7.1 Approach

Use verified templates with structured content and explicit answer keys. This is L2-M3, not part of the first Review release.

Potential template families:

1. Meaning recognition: select the correct meaning of a word in context.
2. Word selection: choose a suitable word for a sentence.
3. Conjugation: fill in the correct verb form for a specified subject/tense.
4. Sentence completion: fill a missing word or short phrase.
5. Short written response: answer a clear question or produce a short sentence.
6. Later: listening-based identification, comprehension, and transformation.

**Avoid ambiguity:** Multiple valid Spanish phrasings may exist. Written-answer grading must not assume one exact string is the only correct answer.

**Depends on:** a verified content source for meanings and forms. None exists yet (§15).

### 7.2 Generation rules

- Select a concept based on learner history and available verified content.
- Choose an applicable template and a validated example.
- Verify the intended answer and acceptable alternatives.
- Avoid presenting the exact same sentence repeatedly as the main measure of mastery.
- If no reliable question can be generated, skip it.
- Shorten the review rather than fabricating extra questions.

### 7.3 Future AI-assisted tools

A future design option is to let the LLM **call constrained scripts/tools**, rather than freely generate entire exercises. For example:

```text
choose_concept()
  -> select_template(concept, target_skill)
  -> retrieve_verified_sentence(concept)
  -> fill_template(sentence, concept)
  -> validate_question_and_answers()
  -> present_question()
```

The AI could suggest a context or candidate sentence, but the app should validate content and retain control of the question structure and grading. This is a **future idea**, not a prerequisite for any planned milestone.

## 8. Listening practice — future update

### Desired experience

- Use **realistic everyday conversations**.
- Introduce only a few unfamiliar words per clip or sentence.
- Have the learner identify meaningful words, especially verbs and nouns, while gradually learning connecting speech.
- Address natural word blending and rapid speech (examples: *vas a*, *van a*, *tengo que*, *me da*).
- On a miss: reveal/explain relevant words, replay more slowly, then ask about the concept in a **new sentence**.
- Save results as listening-specific evidence.

### Suggested learning loop

```text
Listen -> Identify -> Reveal/explain -> Slow replay -> New context -> Record evidence
```

### Later implementation questions

- Audio source: verified recordings, local text-to-speech, or other approved sources?
- Playback speed and replay limits?
- How to measure understanding without punishing a learner for unimportant filler words?
- How to keep vocabulary difficulty appropriate?
- How to score blended expressions and multiword phrases?

## 9. Speaking practice — future update

**Primary experience:** a learner speaks into a microphone to a character in a realistic scenario.

Example: a waiter asks a question; the learner responds in Spanish; the waiter continues the exchange.

Rules:

- Conversation should flow naturally.
- When the learner is stuck, the character should **rephrase or simplify in Spanish** rather than immediately give the complete answer.
- Save corrections and detailed grammar feedback **until after** the conversation.
- Track whether a question had to be simplified; that assistance matters when interpreting skill evidence.
- Track communication success separately from grammatical accuracy.
- The same conversation framework may eventually support boss battles.

### Open technical questions

- Speech-to-text and text-to-speech options that meet offline-first goals.
- How to handle recognition mistakes versus actual learner mistakes.
- How to handle delays from local inference and background grading.
- Accessibility and a text-based fallback.

## 10. Boss battles and rank promotion — future update

Boss battles are **realistic conversational assessments**, not large memorization quizzes.

### Core loop

1. Learner becomes eligible through the progression system (exact XP gate TBD).
2. Launch a scenario, such as ordering food at a café.
3. Character responds based on the learner's actions.
4. Evaluate communication, task completion, and grammar.
5. Present a clear rubric and feedback.
6. On failure: assign targeted practice **and** start a short cooldown.
7. Permit another attempt after remediation and cooldown requirements are satisfied.

### Grading philosophy

- Successful communication is central.
- Minor grammar errors should not necessarily fail the learner.
- Serious or repeated errors that alter meaning can affect the result.
- Record weaknesses by concept and modality.
- Do not claim the learner passed simply because the model produced a positive-sounding reply.

### Still to specify

- Pass thresholds and severity weighting.
- Cooldown length.
- Required remediation amount.
- Scenario pool and variation.
- Whether each rank uses the same rubric or becomes more demanding.
- Voice versus text availability in early boss-battle releases.

## 11. Daily and weekly challenges — future update

### Confirmed direction

- Start with a **shared rotating challenge bank**, not a personalized challenge generator.
- Offer daily and weekly challenges with bonus XP.
- Completion should be **demonstrated** when a challenge tests learning, not just self-reported.
- Completing a challenge does not mark its words permanently mastered.
- Previously learned words should still appear in reviews, sentences, and conversations.

Example challenges (illustrative, not finalized):

- Learn and demonstrate understanding of three new verbs.
- Correctly use a target verb in two different contexts.
- Complete a Daily Review.
- Finish a short listening activity.

### Proposed implementation

- Curated challenge definitions with type, target, time window, and reward.
- Automatic daily/weekly rotation.
- Progress derived from recorded activity/evidence where possible.
- One-time reward per challenge instance; prevent easy XP farming.
- Later: broaden the challenge bank and add variety.

## 12. Learning recommendations and skill profiles

The learner should see **why** a skill is considered strong or weak.

A useful skill explanation should cite actual practice evidence, for example:

> “You recognized *tener* correctly across several sentences, but your verb conjugation answers remain inconsistent.”

Do **not** show fabricated improvement statements when data is insufficient.

### Recommendation policy

Balance:

- Previously missed concepts that need review.
- Concepts the learner has not tested recently.
- New material, so progress does not stall.
- Occasionally verified familiar concepts.

Keep recommendations optional rather than forcing every session into remediation.

### Modalities

Reading, writing, listening, and speaking should have distinct evidence. A multiple-choice vocabulary question should not be treated as equivalent to successfully using a word in a spoken conversation.

## 14. Acceptance tests for later features

Acceptance tests for Recap and Review are in `LEVEL2_RECAP_REVIEW_PLAN.md`.

### Templates and dictionary (L2-M3)

- [ ] An unavailable local AI model does not prevent template-based review.
- [ ] Review with only two good questions shows two questions.
- [ ] Each question has a verified correct answer or a defensible grading method.
- [ ] Unconfirmed AI suggestions do not enter confirmed learning history.
- [ ] Familiar words can reappear in later reviews.
- [ ] Repeated identical questions do not falsely inflate mastery.
- [ ] Skill estimates do not swing wildly after one session.

### Challenges and bosses

- [ ] Challenge completion does not retire its concepts.
- [ ] Repeated challenge submissions cannot farm rewards.
- [ ] Boss failures provide targeted practice and a cooldown.
- [ ] A conversationally understandable minor grammar error is not automatically a fail.
- [ ] Serious meaning-changing mistakes affect boss outcomes.
- [ ] Speaking assistance is recorded without being treated as fully independent performance.

## 16. Working agreement for future updates

Before implementing a feature:

1. State the **learner problem** it solves.
2. Check **what the repository already has** and write it down before listing tasks.
3. Define the **smallest usable version**.
4. Identify what **learning evidence** it produces.
5. Separate **XP/rewards** from **mastery/skill**.
6. Prefer **verified rules/templates** over unnecessary LLM generation.
7. Define what happens when content, history, or AI output is missing.
8. Add tests for ambiguous grading, repeated attempts, and misleading progress.
9. Ship, use the app personally, then revise based on actual experience.

---

**North star:** Language AI should be able to explain not just *how much* a learner has studied, but **what they can reliably understand and do**, where they struggle, and what practice will help next.
